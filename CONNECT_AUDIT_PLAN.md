# Connect для Prop Controller — аудит и план

Статус: **на утверждение.** Код не менялся. Реализация начнётся после
подтверждения, что версия 0.12 собрана и проверена на телефоне,
и после ответов на вопросы в конце документа.

---

## 1. Как сейчас устроен Messenger (аудит)

### Технологии и сборка

| Что | Как устроено |
|---|---|
| Язык, фреймворк | **Flutter / Dart 3**, только Android. Kotlin/Java не используются: нативная часть — стандартная, её генерирует Flutter. |
| Сборка | GitHub Actions, Flutter stable (3.41+). Папка `android/` создаётся `flutter create` при каждой сборке; `tool/prepare_android.sh` дописывает манифест (разрешения), Gradle (desugaring для уведомлений) и иконки. Версии AGP/Kotlin — из шаблона Flutter, проект их не фиксирует. |
| Плагины | sqflite, path_provider, file_picker, video_player, just_audio, camera, record, flutter_local_notifications |

### Структура кода

| Папка | Что внутри |
|---|---|
| `lib/app/` | службы (`AppServices`), движок сцен, звонки, импровизация, уведомления, навигация, пульт громкостью, кинорежим |
| `lib/core/` | дизайн-система, бренд, утилиты |
| `lib/data/` | SQLite: схема и миграции, модели, репозитории, демо-данные |
| `lib/features/` | экраны |

### Как устроены данные и логика

| Что | Как устроено |
|---|---|
| Состояние | Без ViewModel и сторонних менеджеров состояния. `AppServices` — один контейнер служб (передаётся через `InheritedWidget`). Экраны читают базу через `LiveQuery`: после любой записи в таблицу экран перечитывает её сам. Движки — `ChangeNotifier`. |
| База | SQLite (sqflite), схема v1 с версионными миграциями. 14 таблиц: персонажи, телефоны, контакты телефонов, чаты, участники чатов, сообщения, медиа, сцены, участники сцен, действия, дубли, звонки, заготовки, настройки. |
| «Пользователи» | **Персонаж** существует один на всё приложение. **Виртуальный телефон** — точка зрения, у него есть владелец-персонаж. **Контакт** — то, как персонаж записан на конкретном телефоне («Красотка»). |
| Чаты | Личные чаты на каждом телефоне. **Группы заложены в базе, но не реализованы**: нет экрана, имён отправителей в пузырях, событий «добавил в группу». |
| Сообщения | `MessageRepository`. Типы: текст, фото, видео, аудио, голосовое, видеосообщение, файл, событие, звонок. Статусы: отправляется → отправлено → доставлено → прочитано, не отправлено. «Удалено» — отдельный флаг. Происхождение: база, сцена или импровизация — на этом держится сброс. |
| Звонки | `CallEngine` отделён от экрана. Состояния: входящий, вызов, соединение, разговор, завершён. Одновременно идёт один звонок. История пишется в базу и в чат. |
| Уведомления | `NotificationService`: каналы, звук, переход в чат. Уведомление приходит само, когда в неоткрытый чат попадает входящее. |
| Медиа | Медиатека с id; файлы копируются во внутреннюю папку приложения. |
| Навигация | `AppNavigator` — явный список переходов: чат, профиль, экран звонка, «в кадр», назад. |
| Действия | **`SceneEngine` + `SceneDataEffects`** — уже готовый «исполнитель действий от имени персонажа». Действие выполняется от имени участника в его чате. У каждого шага есть журнал отмены: «Назад» и «СБРОС СЦЕНЫ» работают, в том числе после перезапуска. Действия бывают ручные и из таймлайна. |

### Что важно для Connect

1. **Сетевого кода в приложении нет, и в релизном манифесте нет
   разрешения INTERNET.** Шаблон Flutter добавляет его только
   в отладочные сборки. Без него релизный APK не откроет даже локальное
   соединение — это обязательная правка.
2. **Почти всё, что должен уметь Connect, уже умеет движок сцен:**
   сообщения, медиа, «печатает…», удаление, статусы, звонки, уведомления,
   переходы, «время в кадре», отмена и сброс. Connect не нужно учиться
   менять данные Messenger — ему нужно передавать команды этому
   исполнителю.
3. **Группы** придётся сначала сделать в самом Messenger, иначе
   групповые команды будут отвечать UNSUPPORTED_ACTION.

## 2. Где разместить Connect

Отдельный слой `lib/connect/`. Он не знает об экранах и обращается только
к службам Messenger:

```
Prop Controller
    │  Wi-Fi / LAN, WebSocket, зашифрованные кадры
    ▼
lib/connect/transport/   сервер WebSocket (dart:io), heartbeat, переподключение
    ▼
lib/connect/security/    сопряжение, ключи (Android Keystore), сессии, права
    ▼
lib/connect/protocol/    Prop Control Protocol v1: кадры, команды, ответы, коды ошибок
    ▼
lib/connect/dispatch/    реестр действий (whitelist) → обработчик на каждый ActionType,
                         проверка параметров, очередь команд, SEQUENCE / DELAY / CANCEL
    ▼
существующее ядро        SceneEngine/SceneDataEffects, CallEngine, репозитории,
                         NotificationService, AppNavigator (только перечисленные переходы)
    ▼
существующий UI          обновляется сам через LiveQuery — Connect его не трогает
```

- **Экран Connect:** Настройки → Дополнения → Connect и карточка
  в операторской. В кинорежиме пункт скрыт, как остальные служебные.
- **Журнал Connect** — отдельный, без токенов и ключей.

### Ключевое решение: «сцена Connect»

Всё, что делает Controller, выполняется внутри сцены:
- если Controller указал сцену — в ней;
- если нет — в служебной сцене «Connect» этого телефона. Она создаётся
  автоматически, участники добавляются по мере команд.

Что это даёт:
- **RESET_SCENE работает сразу и безопасно.** Удаляется только то, что
  добавили команды, пользовательские данные не трогаются. Журнал сцены
  переживает перезапуск.
- **Ничего не создаётся «мимо» модели данных:** сообщения — настоящие
  сообщения Messenger, звонки — настоящий CallEngine.
- **«Назад» с пульта громкостью** отменяет и команды Controller.

## 4. Минимальные изменения существующего кода

1. `tool/prepare_android.sh`: разрешения INTERNET, ACCESS_NETWORK_STATE,
   ACCESS_WIFI_STATE, CHANGE_WIFI_MULTICAST_STATE (для поиска в сети).
2. `SceneEngine`: метод выполнения одной команды **с результатом** —
   успех, ошибка, id созданного сообщения. Сейчас ручные действия пишут
   ошибки только в журнал. Существующие методы не меняются.
3. `SceneDataEffects`: вернуть id созданного сообщения; удаление и правка
   по id сообщения (сейчас — «последнее сообщение участника»).
4. `MessageRepository`: правка текста с пометкой «изменено» (флаг в базе
   уже есть).
5. `AppServices`: служба `connect` (запуск и остановка).
6. «Дополнения» и операторская: пункт Connect.
7. `pubspec.yaml`, новые пакеты:
   - `flutter_secure_storage` — ключи в Android Keystore, нативный плагин;
   - `cryptography` — шифрование, чистый Dart.

   Всё остальное (сервер, UDP-поиск, IP-адреса) — стандартная библиотека
   Dart, без плагинов.

Экраны, модели, схема базы и дизайн **не меняются**.

## 5. Что можно отдать под управление сразу

MESSAGE (текст; от персонажа владельцу телефона и наоборот), MEDIA_MESSAGE
(фото, видео, голосовое, видеосообщение из медиатеки), TYPING,
DELETE_MESSAGE, MESSAGE_STATUS (доставлено, прочитано), CALL, VIDEO_CALL,
ACCEPT_CALL, DECLINE_CALL, END_CALL, NOTIFICATION, OPEN_SCREEN (чат,
список чатов, профиль), DELAY, SEQUENCE, CANCEL, RESET_SCENE, а также
служебные команды PING, GET_INFO, LIST_CHARACTERS, LIST_CHATS, LIST_MEDIA.
Служебные нужны Controller, чтобы знать id персонажей и файлов, а не имена
кнопок.

## 7. Сеть, безопасность, устойчивость — предлагаемые решения

**Транспорт.** Messenger — сервер WebSocket в локальной сети (`dart:io`,
порт по умолчанию 47620). Controller — клиент. Интернет не нужен.

**Поиск.** Messenger рассылает UDP-сообщение о себе в локальную сеть:
Device ID, имя, порт, версия протокола — без секретов. На экране Connect
всегда виден IP:порт для ручного ввода: некоторые роутеры блокируют
широковещание (режим «изоляции клиентов»).

**Сопряжение.** Похоже на сопряжение Bluetooth-устройств:
1. На Messenger: «Разрешить подключение» → режим сопряжения на 2 минуты.
2. Устройства обмениваются открытыми ключами (X25519).
3. **Оба экрана показывают один и тот же 6-значный код**, вычисленный
   из обоих ключей.
4. Оператор сверяет коды и нажимает «Разрешить» **на Messenger**.

Посторонний в той же Wi-Fi не сможет незаметно встать посередине: коды
не совпадут. Доверенный Controller запоминается и отзывается одной кнопкой.

**Сессии.**
- При каждом подключении — проверка ключа доверенного устройства
  «вызов — ответ» и новый сеансовый ключ.
- Все кадры после этого зашифрованы (AES-GCM) и защищены от повтора.
  Отдельный TLS-сертификат не нужен.
- Сессия истекает, по умолчанию через 12 часов. Её можно завершить
  с любой стороны.

**Хранение секретов.** Ключи Messenger и список доверенных устройств —
в Android Keystore через `flutter_secure_storage`. В базе, журнале
и в коде секретов нет.

**Права доверенного устройства:** VIEW, CONTROL, MESSAGES, CALLS, MEDIA,
GROUPS, SCREENS, RESET. Сейчас по умолчанию «всё», позже выдаются
выборочно — без переделки протокола.

**Что запрещено на уровне кода:**
- Только перечисленные ActionType. Неизвестный тип → UNKNOWN_ACTION.
- Никаких путей к файлам: медиа только по id медиатеки.
- Никаких Activity, Intent, shell или кода: экраны только из списка
  OPEN_SCREEN.
- Проверка и ограничение размеров всех параметров.

**Device ID.** Случайный идентификатор, созданный при первом включении
Connect, показывается как `MESSENGER-7F32A1`. IMEI и серийные номера
не используются. Имя телефона («Телефон Ивана») редактируется.

**Очередь.**
- Одна последовательная очередь команд на Messenger: состояние меняется
  строго по одной команде.
- SEQUENCE — одна задача в очереди.
- У каждой команды есть политика: `QUEUE` (по умолчанию, до 50 в очереди)
  или `REJECT_IF_BUSY` → DEVICE_BUSY.
- CANCEL останавливает идущую последовательность.

**Команды не теряются молча.**
- Повторная команда с тем же commandId (после переподключения)
  не выполняется второй раз: Messenger возвращает прежний ответ из кэша
  последних 500.
- Ответ, который не удалось отправить, повторяется после переподключения.

**Время и синхронизация нескольких телефонов.**
- PING/PONG с отметками времени даёт Controller смещение часов каждого
  телефона.
- У команды есть необязательный `executeAt` — выполнить в момент по часам
  Messenger. Так Controller сможет запускать события на трёх телефонах
  одновременно. Саму логику синхронизации сделает Controller.

**Фон и экран.** На площадке телефон с Messenger обычно на экране, в кадре.
- **Режим «экран включён»** (по умолчанию): сервер работает, пока
  приложение видно. Потеря Wi-Fi → статус «Переподключение» и ожидание.
  Controller переподключается сам.
- **Режим «в фоне»** (по вашему выбору): foreground-сервис
  с типом `connectedDevice` и постоянным уведомлением. Иначе Android
  (особенно Xiaomi и Huawei) усыпит сеть приложения. Минус: уведомление
  видно в шторке, то есть может попасть в кадр. Поэтому это отдельная
  настройка, а не поведение по умолчанию.

## 8. Протокол (набросок v1)

Кадр — JSON в зашифрованной обёртке:

```json
{
  "protocolVersion": 1,
  "commandId": "c-0192",
  "targetDeviceId": "MESSENGER-7F32A1",
  "actionType": "MESSAGE",
  "timestamp": 1790000000000,
  "executeAt": null,
  "policy": "QUEUE",
  "sceneId": null,
  "payload": { "fromCharacterId": "char-masha", "toCharacterId": "char-ivan", "text": "Ты где?", "typingMs": 2000 }
}
```

Ответ:

```json
{ "protocolVersion": 1, "commandId": "c-0192", "status": "SUCCESS",
  "errorCode": null, "message": "", "timestamp": 1790000000150,
  "result": { "messageId": "…" } }
```

**Статусы:** SUCCESS, FAILED, UNSUPPORTED_ACTION, UNKNOWN_ACTION,
DEVICE_BUSY, NOT_FOUND, NOT_AUTHORIZED, SESSION_EXPIRED, INVALID_PARAMETER,
CANCELLED, INTERNAL_ERROR.

**SEQUENCE:**
```json
{ "actionType": "SEQUENCE", "payload": { "stopOnError": true, "steps": [
  { "actionType": "MESSAGE", "payload": { "fromCharacterId": "char-masha", "toCharacterId": "char-ivan", "text": "Ты где?" } },
  { "actionType": "DELAY", "payload": { "ms": 3000 } },
  { "actionType": "CALL", "payload": { "fromCharacterId": "char-masha", "toCharacterId": "char-ivan" } },
  { "actionType": "DELAY", "payload": { "ms": 10000 } },
  { "actionType": "END_CALL", "payload": {} }
]}}
```

Ответ на SEQUENCE содержит результат каждого шага. Шаги выполняются
тем же исполнителем, что и одиночные команды.

**«Кто кому».** Телефон показывает мир глазами своего владельца:
- `to` = владелец телефона — входящее от `from`;
- `from` = владелец — исходящее к `to`;
- если ни `from`, ни `to` не владелец — до появления групп
  INVALID_PARAMETER.

Какой персонаж владелец, Controller узнаёт через GET_INFO.

Полная документация — `PROP_CONTROL_PROTOCOL.md`: поиск, подключение,
сопряжение, все ActionType с параметрами, ошибки, примеры. Пишется
вместе с реализацией.

## 9. Проверка без Prop Controller

**Connect → «Проверка».** Внутри Messenger запускается встроенный тестовый
клиент. Он подключается к собственному серверу Connect по настоящему
сокету (127.0.0.1), проходит сопряжение и аутентификацию и отправляет
команду, например `MESSAGE Маша → Иван «Тест Connect»`. Ответ SUCCESS
и сообщение видны сразу. Проверяется весь путь, кроме Wi-Fi.

**Автотесты** (запускаются на GitHub при каждой сборке):

| Группа | Что проверяется |
|---|---|
| Протокол | разбор и сборка кадров, версии, коды ошибок |
| Безопасность | неизвестное устройство, неверный ключ, просроченная сессия, повтор кадра, запрещённая команда, неизвестный ActionType, отозванное устройство |
| Соединение | через настоящий WebSocket на localhost: подключение, отключение, переподключение, повтор commandId без дублирования |
| Действия | на настоящей SQLite: сообщение, неизвестный отправитель или получатель, пустой текст, неподдерживаемый тип, звонок и его завершение, чужой звонок, медиа по id, открытие экрана |
| SEQUENCE | несколько шагов, DELAY, ошибка внутри, CANCEL |
| Группы | UNSUPPORTED_ACTION до этапа C3 |

**Физическая проверка на телефоне (с Wi-Fi):** только вами. В отчёте будет
отмечено NOT PHYSICALLY VERIFIED, пока не пришлёте результат.

## 11. Нужны ваши решения

1. **Сопряжение** сверкой 6-значного кода на двух экранах и кнопкой
   «Разрешить» на Messenger — подходит?
2. **Работа при погашенном экране или свёрнутом приложении** нужна?
   Если да — это постоянное уведомление в шторке (C2).
3. **Группы** нужны уже в первом этапе или можно этапом C3 после ядра?
4. **«Кто кому».** Верно ли, что «Иван» в командах — всегда владелец
   телефона, на котором это отображается (как в примере «Маша пишет Ивану»
   → на телефоне Ивана)?
